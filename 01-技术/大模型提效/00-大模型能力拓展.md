# 大模型能力拓展 - 内部培训（40-50分钟）

> [!abstract] 培训概览
> **目标**：大模型能力扫盲，帮助团队建立正确的 AI 协作认知与实操能力
> **时长**：40-50 分钟 | **节奏**：理论 25min + 实操演示 15min + 答疑 5-10min
>
> **受众**：日常需要写文档/方案/代码/汇报的同学（不要求懂算法）
>
> **演示**：在第三部分（效果优化）穿插实操 — 用 PromptPilot 演示 Prompt 优化、用 Cursor 现场展示 MCP 调用 Excel/Word、用 Cursor Agent 模式完成一个小任务（从“需求→计划→执行→验证”）。

## 术语

| 术语           | 一句话理解                                                   | 你在工作里怎么用                    |
| ------------ | ------------------------------------------------------- | --------------------------- |
| Token        | 模型“读写文本”的计量单位（不是字数）：1 个汉字 ≈ 1.5 token，1 个英文单词 ≈ 1 token | 理解“上下文窗口为什么会满”，学会做摘要/拆分     |
| Context（上下文） | 本轮推理时模型“能看到”的全部信息                                       | 把文档/约束/历史决策放进去，别只给一句话需求     |
| Prompt       | 你给模型的指令与任务描述                                            | 用“角色+背景+任务+要求”写清楚           |
| Schema       | 强制输出结构（JSON/表格/固定字段）                                    | 让输出可解析、可复用、可对接系统            |
| Rule         | 约束边界与禁止项                                                | 防越权、反幻觉、反编造（尤其工程化与合规场景）     |
| RAG          | 先检索资料，再生成答案                                             | 私域知识/最新信息场景必备，且要强调引用来源      |
| Agent        | 会拆任务、调工具、做循环                                            | 适合“多步骤、有反馈”的任务；先 Plan 再执行更稳 |

### 大模型认知

> 核心理念参考：[vibe-coding-cn](https://github.com/2025Emma/vibe-coding-cn)
### 核心理念

> [!info]
**第一性原则：上下文是一切的基础**


- 垃圾进，垃圾出（GIGO）- 输入质量决定输出质量
- 上下文包括：**需求文档、技术栈、架构设计、历史决策、代码规范等**
- **关键：规划先行，避免“未经确认就执行”**（可以让 AI 产出计划，但要先审查再执行）

> [!info]
**目的驱动开发**

- 开发过程中的一切动作围绕"目的"展开
- 先明确需求，从需求逆向构建代码
- 一次只做一件事，避免范围蔓延；多次交互建议新开 session（会话），避免上下文污染

> [!info]
**能自动化就不手工**
- 凡是 AI 能做的，就交给 AI 做
- 一切问题先问 AI，利用其知识库和推理能力
- 专注于高价值决策，让 AI 处理重复性工作
### 实践方法
**规划驱动工作流（建议现场口播 20 秒）**

需求澄清 → 技术选型 → 架构设计 → 分步实施 → 测试验证 → 文档同步
**开发黄金法则**
1. **一句话目标 + 非目标** - 明确做什么、不做什么
2. **文档即上下文** - 文档不是事后补，是开发必需品
3. **接口先行，实现后补** - 先定义清晰的接口契约
4. **一次只改一个模块** - 降低出错概率，便于回滚
5. **能复用不重写** - 优先寻找已有轮子，询问 AI 推荐方案
### 关键技巧
**边界控制**
- 明确告诉 AI：**能改什么，不能改什么**
- 使用 RULE.md 或系统提示词固化开发规范
- 防止 AI 擅自修改不相关代码

**上下文管理**
- 代码一多就切换新会话，避免上下文污染
- 使用 Memory Bank 保存核心文档（需求、架构、进度），人工精炼上下文
- 定期同步 `progress.md` 和 `architecture.md`
**代码质量**
- 官方文档优先 - 先把官方文档喂给 AI
- 正交性 - 功能模块职责清晰，避免过度耦合
- 奥卡姆剃刀 - 如无必要，勿增代码
### 避坑指南
❌ **千万别做**
- 让 AI 自由发挥架构设计
- 不提供上下文就让 AI 写代码
- 把整个项目代码丢给 AI 让它"优化"
- 忽略 AI 生成的测试代码直接提交
✅ **推荐做法**
- 先人工审查 AI 生成的计划，确认后再执行
- 保持小步快跑逐个子计划执行，每个功能点都验证在进行下一个
- 建立项目级的 RULE.md规范 AI 行为
- 使用版本控制工具，随时可回滚

## 第三部分：大模型效果优化的基础内容

> [!note] 思路
> **概念 + 例子 + 实操** — 每个模块都建议配合实际演示（如 Cursor、PromptPilot）

> [!tip] 15 分钟
> - **必讲**：Prompt/Schema/Rule（把话说清楚 + 不越界）  
> - **点到为止**：Memory/RAG（告诉大家“窗口有限、需要检索”）  
> - **用演示带过**：MCP/Agent/Skills（让大家看到“能读文件、能执行步骤”即可）

> [!important] 主线概念
> - **Prompt / Schema**：把“要什么”说清楚（[[#Prompt 提示词]]、[[#Schema Prompt（结构化提示词）]]）  
> - **Rule**：把“不能做什么”说清楚（[[#Rule（规则）]]）  
> - **Memory / RAG**：让模型“记得住 / 查得到”（[[#Memory模型记忆]]、[[#RAG（Retrieval-Augmented Generation，检索增强生成）]]）  
> - **Agent / MCP / Agent Skills**：让模型“能动手做事”（[[#Agent智能体]]、[[#MCP（Model Context Protocol模型上下文通讯协议）]]、[[#Agent Skills（可复用能力单元）]]）

### 安全与合规（建议先讲 1 分钟）

- **三条红线**：不传密钥/账号；不传客户与个人敏感数据；不让 AI 直接改生产（先 Plan、再评审、再执行）。
- **两条习惯**：先脱敏再粘贴；输出要“可追溯”（让 AI 标注依据来自哪里：文档/代码/工具返回）。

### 实操演示脚本（ 15 分钟）

> [!note] 目标：让大家看到“同一个任务，输入不同 → 输出差异巨大”
> 建议选择一个**大家熟悉的真实任务**（如“写技术方案大纲 / 分析一张 Excel / 重构一段小代码”），并确保素材已脱敏。

1. **Prompt 优化（5min）**：同一个问题先用“坏 Prompt”问一次，再按“角色+背景+任务+要求”补齐上下文重问一次，对比差异。
2. **MCP 拓展上下文（5min）**：让 Cursor 读取一份 Excel/Word，提问“基于表格做结论 + 风险 + 下一步”，观察模型工具调用与返回内容。
3. **Agent 小任务（5min）**：先 Plan 输出步骤与改动范围 → 人工确认 → 再让 Agent 执行 1-2 个小步骤（强调可回滚与最小改动）。

### Prompt 提示词

**用来规范、优化模型输出**，常用的提示词优化工具：[PromptPilot](https://promptpilot.volcengine.com/)

**基础 Prompt 公式：**

**Prompt = 角色（Role）+ 背景（Context）+ 任务（Task）+ 要求（Constraints）**

模板：

```text
你是一名【角色】。
背景：
【当前系统 / 环境 / 约束说明】
任务：
【明确要完成的事情】
要求：
1. 【输出风格】
2. 【结构 / 格式】
3. 【深度 / 范围】
4. 【其他限制】
```

举例：

```text
你是一名有多年经验的云原生架构师。
背景：
我们在华为云环境中部署 Kubernetes 集群，
当前使用 MetalLB 提供 VIP，
计划切换为华为云 ELB，避免 VIP 漂移风险。
任务：
请评估该切换方案的技术可行性，
并给出一套本地验证方案。
要求：
1. 使用通俗易懂的语言
2. 按步骤列出验证流程
3. 指出至少 3 个潜在风险点
4. 使用 Markdown 输出
```

⚠️ 注意点：**以上任意一点不写都会严重影响模型输出效果**，建议用 PromptPilot 现场做一次“坏 Prompt → 好 Prompt”的对比演示。

> [!tip] 现场可用的“提效三板斧”
> 1）先让 AI **反问澄清**（先问 3-5 个问题再回答）  
> 2）给 **一个好例子 + 一个坏例子**（更好控制边界）  
> 3）强制 **输出结构**（标题/表格/JSON）

### Schema Prompt（结构化提示词）
用“固定格式”约束模型输出，**主要用于对接应用开发**
限制模型输出为JSON、markdown、html等格式。
**模板 1：评估类（最常见）**

```text
你是一名【角色】。
背景：【环境说明】
任务：请对【目标】进行评估。
要求：先给结论，再给要点，最后给风险与建议。
```

```json
{
  "conclusion": "",
  "key_points": [],
  "risks": [],
  "suggestions": []
}
```
---

**模板 2：规划类（Agent Planning）**
```json
{
  "goal": "",
  "plan": [
    {
      "step": 1,
      "action": "",
      "dependency": "",
      "risk": ""
    }
  ]
}
```

### Rule（规则）

本质也是一种 Prompt，用于**严格限制模型的行为**。建议写 Prompt 前先写 Rule：把**不能做什么、必须遵守什么**固定下来，剩下的再交给 Prompt。

```text
【Rule】
1. 不允许修改智算平台源码
2. 不允许虚构不存在的系统或配置
3. 不确定信息必须明确说明
【Prompt】
角色：
你是一名云原生架构师。
背景：
当前在华为云环境中部署 Kubernetes，
计划从 MetalLB 切换为华为云 ELB。
任务：
评估该切换方案的可行性。
要求：
1. 给出可执行步骤
2. 指出风险点
```

**综合示例：Prompt + Rule + Schema 组合**
```text
【Rule】
1. 不允许修改智算平台源码
2. 不允许虚构不存在的系统、组件或配置
3. 不确定的信息必须明确标注为“不确定”
【Prompt】
你是一名云原生架构师。
背景：
当前在华为云环境中部署 Kubernetes 集群，
原使用 MetalLB 提供 VIP，
现计划切换为华为云 ELB。
任务：
请评估该切换方案的可行性。
【Schema】
请严格按以下 JSON 输出，不要输出多余内容：
{
  "conclusion": "可行 | 不可行 | 有条件可行",
  "key_assumptions": ["前提条件1"],
  "advantages": ["优点1"],
  "risks": [
    {
      "description": "风险说明",
      "level": "高 | 中 | 低"
    }
  ],
  "verification_steps": [
    {
      "step": 1,
      "action": "具体可执行操作"
    }
  ]
}
```


### Memory模型记忆
模型的长期记忆，要和上下文（context）、token 做区别。
模型本身只接收一段文本（tokens），  Context / Memory 都是“被系统拼进去的”。
真实 Context 拼接示例（展开讲）

```text
【System / Rule】 
你是一个严谨的企业级 AI 助手...  
【Injected Memory】 
用户角色：Java 架构师 偏好：通俗解释 + 可执行步骤  
【RAG 结果】 
（从文档中检索到的 3 段内容）  
【对话历史】
 用户：xxx 助手：yyy  
【当前 Prompt】
 请评估 MetalLB 切换 ELB
```

Memory 一般是存储在本地或服务端（取决于产品形态）。工程化应用通常会做：**对话摘要（短期）**、**长期偏好/画像（长期）**、**知识库检索（RAG）**，最后由“上下文拼装器”统一注入到本轮 Prompt。
```markdown
本地存储
  ├─ Memory（长期）
  ├─ 对话历史
  ├─ RAG 结果
        ↓
  Context Builder（拼装器）
        ↓
  最终 Prompt（tokens）
        ↓
       LLM
```

> ⚠️ 注意：**大模型厂商说的「100K / 200K token 窗口」= 模型一次推理时，能“同时看到”的全部上下文 token 上限**  
👉 **包含：system / rule / prompt / memory / 历史对话 / RAG 内容 / 工具返回**

不是“长期记忆”，也不是“存储能力”，而是**单次推理的“可见上下文长度”**。举例：Cursor/IDE 客户端里 system prompt、规则、历史对话、工具返回都会占用窗口。
```text
[System Prompt / Rule]
[Schema Prompt]
[Developer Prompt]
[历史对话 N 轮]
[Memory（摘要/长期记忆注入）]
[RAG 检索到的文档]
[工具调用结果]
--------------------------------
<= 总 token 数 ≤ 100K / 200K
```

| 维度 | 分类 | 核心 | 怎么用 | 举例 |
|:---|:---|:---|:---|:---|
| 生命周期 | **短期 Memory**  | 为“当前任务”服务，用完就可以丢                   | 不写数据库，不做向量化、不长期保存<br>**会话中 → 自动总结 → 注入下一轮 prompt**                                                 | ChatGPT、Qwen等自动多轮对话记忆             |
| 生命周期 | **长期 Memory**  | 跨任务、跨时间仍然有价值的信息                    | 大模型里的典型内容、用户偏好、用户背景、稳定习惯、长期目标<br>**用户行为 → 触发规则 → 存入 Memory Store**<br>**请求时 → 挑选相关的 → 注入 context** | Cursor 中的 Skill、或者 ChatGPT、Qwen 分组功能 |
| 作用范围 | **会话级 Memory** | 只对当前这次对话（session）有效，会话一结束，**全部清空** | 本次对话的主题、临时规则、中间结论、对齐共识                                                                             | Cursor 中的会话切换               |
| 作用范围 | **用户级 Memory** | 这个用户以后都这样？                         | 技术水平、表达偏好、使用习惯、长期身份                                                                                | Cursor 中的用户切换                  |

> [!tip] Memory 的“最小可用实践”
> - **只记稳定信息**：角色、偏好、长期目标、常用技术栈（别记临时内容）  
> - **可解释可删除**：让用户能看到/能清理（避免“被记住的不该记”）  
> - **先摘要再注入**：不要把整段历史直接塞回去（噪声会淹没重点）


### RAG（Retrieval-Augmented Generation，检索增强生成）
Prompt / Schema（怎么“说清楚”）、Rule（怎么“不越界”）、Memory（怎么“记得住”）
RAG 解决**两个核心痛点**：

> **Context 窗口再大，也不可能把“所有知识”都塞进去**
> **基础模型是有知识时效性的**


一般来说，基础模型是有知识时效性的，没有RAG或者其他的增强的裸模型，模型的知识是截止在完成训练的时间点。裸模型在**推理时**只能用两样东西，它**不能**：主动上网、自己查数据库、突破训练时间点。
> 训练时学到的统计规律 （预训练、SFT、强化学习等）
当前 Context 里给它的内容

RAG的作用，获取最新知识、私域知识，让模型先“查资料”，再“让模型回答”
`用户问题 → 检索相关资料 → 把资料塞进 Context → 再让模型生成答案`
一般RAG的落地形态：联网搜索、知识库（向量库、结构化数据库）等

> [!note] RAG 快速理解（30 秒版）
> - **索引阶段**：文档切分（chunk）→ 向量化（embedding）→ 入库  
> - **查询阶段**：问题向量化 → 检索 TopK →（可选）重排序 → 拼进 Prompt → 生成

> [!warning] RAG 常见坑（建议至少讲 2 个）
> - **召回不准**：chunk 太大/太小、切分不按语义、TopK 太低  
> - **提示注入**：把不可信内容当“指令”执行（需要 Rule：文档只作参考，不得覆盖规则）  
> - **引用不清**：让 AI 标注“依据来自哪段文档/哪次工具返回”，否则很难审计

### Agent智能体
前面讲了 RAG，模型已经能在回答前查资料了。  但真实工作中，很多任务并不是‘查一次资料就结束’，  而是需要多个步骤、多次判断。  这时候，就需要 **Agent**。
```text
Prompt    → 会回答
RAG       → 会查资料
Agent     → 会拆任务、做决策、串流程
```

**Agent =「大模型 + 一套固定的工具能力 + 一套行为约束配置」**
以Cursor工具为例
```text
Cursor Agent =
1️⃣ 一个基础模型（LLM）
2️⃣ 一个固定的 Agent 执行循环（Plan → Act → Observe）
3️⃣ 一组可调用的工具（Tools / MCP）
4️⃣ 一套行为与约束配置（Role / Rule / Schema）
5️⃣ 一个状态管理机制（Memory / Context）
```

智能体核心：**一个具备“规划能力”的大模型 + 一组可调用的工具 + 一个执行与反馈循环。**
**Goal目标 + Plan计划 + Action执行 + Observation观察 + Loop循环**
 1️⃣ 任务理解（Goal）
你在 Cursor 里输入的不是代码，而是：
> “帮我重构这段代码，并加单元测试”

这不是一句 Prompt，而是：
`目标（Goal）`
---
2️⃣ 规划（Plan）
Cursor Agent 内部会做类似这样的事（你虽然看不到，但它在做）：
`Plan: 1. 阅读当前文件 2. 找到可重构点 3. 修改代码 4. 补充测试 5. 校验是否通过`
👉 这一步就是 **Agent 的“Thought”阶段**
---
3️⃣ 执行（Action）——这一步非常关键
Cursor Agent 能做的事：读取文件、 修改文件、新建文件、搜索代码、执行命令（部分场景）
这些能力**不是模型原生的**，而是：
> **通过 MCP / Tool 层暴露给 Agent 的**

---
4️⃣ 观察（Observation）
每做一步：文件变了、命令返回结果、报错信息
👉 都会作为 **Observation** 回到 Agent。
---
5️⃣ 决策循环（Loop）
`执行结果 OK？ → 是：下一步 → 否：修正方案`
这一步，才是真正的 **Agent 智能体**
---

| 维度 | Cursor Agent | Coze / Dify Agent |
|:---|:---|:---|
| 面向对象 | 开发者 | 产品 / 业务 / 应用 |
| Agent Loop | 内置，不可改 | 内置，但可编排 |
| 工具 | IDE 工具（文件、代码） | API / 插件 / MCP |
| Agent 创建方式 | 配置 Profile | 可视化配置 |
| 是否写代码 | ❌ | ❌ / 少量 |
| 是否多 Agent | ❌ | ✅ |
| 是否流程化 | 隐式 | 显式（流程图） |

---
为什么 Coze / Dify 看起来“更像 Agent 平台”？
因为它们做了 **Cursor 没做、也不适合做的事**：

| 1️⃣ 把 Agent Loop 显式化<br>节点、连线 、条件判断<br>👉 适合**非程序员理解** | 2️⃣ 把 Tool / MCP 标准化<br>`HTTP API 数据库 搜索 RAG 知识库`<br>👉 不再局限 IDE 场景 | 3️⃣ 把 Agent “变成产品”<br>一个 Agent = 一个应用<br>有 ID、有版本、有权限 |
| ------------------------------------------------------ | ------------------------------------------------------------------- | ----------------------------------------------------- |
举例子：
Dify、星辰智能体、星火智能体新建智能体
Cursor新建子智能体以及多种模式
**一句话总览**

> **Ask**：问问题，模型只返回不修改代码
> **Plan**：先想怎么做 ，模型返回后续执行计划给用户确认
> **Agent**：直接帮你干活，综合
> **Debug**：帮你找 bug、修问题，基于错误现象反推问题根因

> [!tip] 现场经验：先 Plan 后 Agent
> 大部分“高风险/有副作用”的任务，建议先用 **Plan** 让 AI 输出步骤与改动范围，人工确认后再切 **Agent** 执行。



### MCP（Model Context Protocol模型上下文通讯协议）

> **MCP = 一套“标准化让大模型调用外部能力”的协议层**

它解决的不是「模型聪不聪明」，而是：

> **模型怎么“安全、可控、可复用、可声明式”地用工具**

```markdown
┌──────────────┐
│   Model      │  ← LLM
└──────────────┘
        ↑
   MCP 协议层（标准）
        ↓
┌──────────────┐
│  Tools / APIs│  ← DB / 文件 / Git / 浏览器 / IDE
└──────────────┘
```

MCP 和 Function Calling / Tool Calling 的关系
```javascript
Function Calling（OpenAI）
Tool Calling（Claude）
        ↓
      MCP（跨模型、跨平台的统一协议）
```

- Function Calling：**厂商私有**
- MCP：**标准化、可复用**
👉 MCP = **Tool Calling 的“HTTP 协议级抽象”**

**MCP 核心组成**
1️⃣ MCP Server（工具提供方）：[魔搭](https://modelscope.cn/mcp?name=excel&page=1)
 2️⃣ MCP Client（模型 / Agent / IDE）：Cursor 的调用配置
3️⃣ Tool Call（不是 Prompt 猜）：Cursor调用过程
**MCP 与 RAG、Agent 的关系**

| 能力 | 解决的问题 | 与 MCP 的关系 |
|:---|:---|:---|
| RAG | 给模型"查资料" | RAG 检索结果可作为 MCP Tool 的输入；也可单独使用 |
| Agent | 拆任务、调工具、做决策 | Agent 通过 MCP 调用工具；MCP 是 Agent 的"工具层" |
| MCP | 标准化工具调用 | 独立协议层，可被 RAG 系统、Agent 共同使用 |

**模型何时使用 MCP 工具？**

- 模型在生成过程中会输出 `tool_call` 类型的 token，表示"我需要调用某工具"
- 触发条件：用户问题涉及外部能力（读文件、查 DB、调 API）时，模型根据 Tool 描述判断是否调用
- 关键：**Tool 的 name、description 要写清楚**，模型靠这些描述决定何时用

❕ **实操示例**：Cursor 中配置 MCP（Excel、Word 读取）→ 提问"请分析这个 Excel 的销售数据"→ 观察模型自动调用 MCP 工具

### Agent Skills（可复用能力单元）

一个“可被 Agent 调用的、可复用的、有明确边界的能力单元”。把**常用的 Tool + 固定步骤 + Prompt 经验**封装成一个“半智能能力块”，让团队可以**复用**而不是“每个人都从零写提示词”。

一个标准的 Agent Skill = 👇

```text
Agent Skill =
1️⃣ 触发条件（什么时候用） 
2️⃣ 内部流程（固定步骤） 
3️⃣ 使用的 Tool（可能多个）
4️⃣ 输入 / 输出 Schema 
5️⃣ 局部 Prompt / Rule
```

举例：Cursor `.cursor/skills`、OpenCode 的 Skills

## 第四部分：日常工作实践

> [!tip] 实践原则
> 所有场景都遵循 [[#核心理念]]：**上下文是一切的基础** — 文档、规范、历史决策先准备好，再交给 AI。

### 场景一：Cursor + 文档进行售前 demo 搭建

**关联能力**：[[#Prompt 提示词]]、[[#Rule（规则）]]、[[#Schema Prompt（结构化提示词）]]

**典型流程**：需求文档 → Cursor 读文档 → 快速搭建验证 demo（如小星畅聊等）

- **关键**：把售前需求、技术栈约束、部署环境写成文档，作为上下文
- **避坑**：不要口头描述，要落到文档；避免 demo 越做越大脱离售前重点

**一段可直接复制的 Prompt（示例）**

```text
你是售前技术负责人。
背景：下面是一份售前需求文档（已脱敏），技术栈限制为【...】，交付时间为【...】。
任务：输出一个“2 天可完成”的 demo 方案：功能列表、架构图要点、关键风险、验证步骤。
要求：只基于文档内容推导；对不确定点先列出澄清问题（<=5 个）；用 Markdown 输出。
```

### 场景二：Obsidian + Cursor 进行年终汇报总结

**关联能力**：[[#Prompt 提示词]]、[[#Schema Prompt（结构化提示词）]]、[[#Memory模型记忆]]

- **Obsidian**：整理全年工作记录、周报、项目成果
- **Cursor**：基于已有文档生成结构化汇报、提炼亮点、补充过渡语
- **核心**：[[#核心理念]] — 你的 obsidian 笔记就是最佳上下文，AI 帮你"组织"而非"编造"

**推荐工作流（3 步）**

1. 先在 Obsidian 汇总素材：周报/项目里程碑/产出链接（可用清单）。
2. 再让 AI 做结构化：按“目标-动作-结果-影响”提炼（避免流水账）。
3. 最后人工补“关键决策与取舍”，这是 AI 最难替代的部分。

### 场景三：Cursor + MCP 进行技术方案编写

**关联能力**：[[#MCP（Model Context Protocol模型上下文通讯协议）]]、[[#RAG（Retrieval-Augmented Generation，检索增强生成）]]、[[#Rule（规则）]]

- **核心理念**：使用 MCP 工具拓展上下文 — 直接读取 Excel、Word、数据库等
- **典型用法**：技术方案需要参考现有架构文档、配置表 → 用 MCP 拉取 → 模型基于真实数据输出
- **工具**：魔搭 MCP（Excel、Word 等）、自建 API 对接

> [!tip] 技术方案写作模板（建议让 AI 先产大纲）
> 背景与目标 → 现状与约束 → 方案选型（含备选）→ 关键设计 → 风险与回滚 → 验证计划 → 排期与分工

### 场景四：Cursor + Agent Skills 进行架构图绘制

**关联能力**：[[#Agent Skills（可复用能力单元）]]

- **核心理念**：使用 Skills 工具规范模型输出 — 避免随意画图、格式混乱
- **Skills 示例**：Mermaid 可视化、Excalidraw 图表、Obsidian Canvas 创建（可参考 Cursor `.cursor/skills` 中的 axton-obsidian-visual-skills）
- **效果**：输入需求 → Skills 约束输出格式 → 直接得到可用的 Mermaid/Excalidraw/Canvas

### 场景五：大模型产品原型设计（实验阶段）

**关联能力**：[[#Prompt 提示词]]、[[#Schema Prompt（结构化提示词）]]、[[#Rule（规则）]]

- **核心理念**：能用 AI 做的就不手动做
- **探索方向**：提示词 → 原型描述 → AI 生成低保真原型、用户故事、验收标准
- **注意**：尚在实验，适合内部验证，不建议直接对外交付

### 核心要点回顾

| 模块 | 一句话记忆 |
|:---|:---|
| 大模型认知 | 上下文是基础，规划先行，能自动化就不手工 |
| Prompt | 角色 + 背景 + 任务 + 要求，缺一不可 |
| Rule | 先写"不能做什么"，再写"要做什么" |
| Schema | 固定格式约束，对接应用开发必备 |
| Memory | 分短期/长期、会话级/用户级，理解 token 窗口 ≠ 长期存储 |

| Agent | 目标 → 规划 → 执行 → 观察 → 循环 |
| MCP | 标准化工具调用协议，跨模型、跨平台 |
| Agent Skills | 可复用的能力单元 = 触发条件 + 流程 + Tool + Schema |
