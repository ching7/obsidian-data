### 核心理念

>[!import]
**第一性原则：上下文是一切的基础**


- 垃圾进，垃圾出（GIGO）- 输入质量决定输出质量
- 上下文包括：**需求文档、技术栈、架构设计、历史决策、代码规范等**
- **关键：规划先行，禁止让 AI 自主规划**

>[!import]
**目的驱动开发**

- 开发过程中的一切动作围绕"目的"展开
- 先明确需求，从需求逆向构建代码
- 一次只做一件事，避免范围蔓延，多次交互新开session或者会话，避免上下文污染

> [!import]
**能自动化就不手工**
- 凡是 AI 能做的，就交给 AI 做
- 一切问题先问 AI，利用其知识库和推理能力
- 专注于高价值决策，让 AI 处理重复性工作
### 实践方法
**规划驱动工作流**
	需求澄清 → 技术选型 → 架构设计 → 分步实施 → 测试验证 → 文档同步
**开发黄金法则**
1. **一句话目标 + 非目标** - 明确做什么、不做什么
2. **文档即上下文** - 文档不是事后补，是开发必需品
3. **接口先行，实现后补** - 先定义清晰的接口契约
4. **一次只改一个模块** - 降低出错概率，便于回滚
5. **能复用不重写** - 优先寻找已有轮子，询问 AI 推荐方案
### 关键技巧
**边界控制**
- 明确告诉 AI：**能改什么，不能改什么**
- 使用 RULE.md 或系统提示词固化开发规范
- 防止 AI 擅自修改不相关代码

**上下文管理**
- 代码一多就切换新会话，避免上下文污染
- 使用 Memory Bank 保存核心文档（需求、架构、进度），人工精炼上下文
- 定期同步 `progress.md` 和 `architecture.md`
**代码质量**
- 官方文档优先 - 先把官方文档喂给 AI
- 正交性 - 功能模块职责清晰，避免过度耦合
- 奥卡姆剃刀 - 如无必要，勿增代码
### 避坑指南
❌ **千万别做**
- 让 AI 自由发挥架构设计
- 不提供上下文就让 AI 写代码
- 把整个项目代码丢给 AI 让它"优化"
- 忽略 AI 生成的测试代码直接提交
✅ **推荐做法**
- 先人工审查 AI 生成的计划，确认后再执行
- 保持小步快跑逐个子计划执行，每个功能点都验证在进行下一个
- 建立项目级的 RULE.md规范 AI 行为
- 使用版本控制工具，随时可回滚

## 大模型效果优化的基础内容
### Prompt提示词
**用来规范、优化模型输出**，常用的提示器优化工具：[promptpilot](https://promptpilot.volcengine.com/)
基础prompt要求：

**Prompt = 角色（Role）+ 背景（Context）+ 任务（Task）+ 要求（Constraints）**

模板：

```text
你是一名【角色】。
背景：
【当前系统 / 环境 / 约束说明】
任务：
【明确要完成的事情】
要求：
1. 【输出风格】
2. 【结构 / 格式】
3. 【深度 / 范围】
4. 【其他限制】
```

举例：

```text
你是一名有多年经验的云原生架构师。
背景：
我们在华为云环境中部署 Kubernetes 集群，
当前使用 MetalLB 提供 VIP，
计划切换为华为云 ELB，避免 VIP 漂移风险。
任务：
请评估该切换方案的技术可行性，
并给出一套本地验证方案。
要求：
1. 使用通俗易懂的语言
2. 按步骤列出验证流程
3. 指出至少 3 个潜在风险点
4. 使用 Markdown 输出
```

⚠️ 注意点：**以上任意一点不写都会严重影响模型输出效果**，使用promptpilop演示

### Schema Prompt结构化提示词
用“固定格式”约束模型输出，**主要用于对接应用开发**
限制模型输出为JSON、markdown、html等格式。
**模板 1：评估类（最常见）**
```json
你是一名【角色】。  
背景： 【环境说明】  
任务： 请对【目标】进行评估。  
请严格按以下 JSON 输出： 
 {   
	 "conclusion": "",   
	 "key_points": [],   
	 "risks": [],   
	 "suggestions": [] 
 }
```
---

**模板 2：规划类（Agent Planning）**
```json
{   
"goal": "",   
	"plan": [     
		{       
		"step": 1,       
		"action": "",       
		"dependency": "",       
		"risk": ""     
		}   
	] 
}
```

### Rule规则
本质也是一种prompt，用于严格限制模型的行为
写 Prompt 前，先写 Rule列出：不能做什么、必须遵守什么，这些全部进 Rule，剩下的才交给 Prompt

```text
【Rule】
1. 不允许修改智算平台源码
2. 不允许虚构不存在的系统或配置
3. 不确定信息必须明确说明
【Prompt】
角色：
你是一名云原生架构师。
背景：
当前在华为云环境中部署 Kubernetes，
计划从 MetalLB 切换为华为云 ELB。
任务：
评估该切换方案的可行性。
要求：
1. 给出可执行步骤
2. 指出风险点
```

一个综合Prompt+Rule+SchekaPrompt的综合提示词
```text
【Rule】
1. 不允许修改智算平台源码
2. 不允许虚构不存在的系统、组件或配置
3. 不确定的信息必须明确标注为“不确定”
【Prompt】
你是一名云原生架构师。
背景：
当前在华为云环境中部署 Kubernetes 集群，
原使用 MetalLB 提供 VIP，
现计划切换为华为云 ELB。
任务：
请评估该切换方案的可行性。
【Schema】
请严格按以下 JSON 输出，不要输出多余内容：
{
  "conclusion": "可行 | 不可行 | 有条件可行",
  "key_assumptions": ["前提条件1"],
  "advantages": ["优点1"],
  "risks": [
    {
      "description": "风险说明",
      "level": "高 | 中 | 低"
    }
  ],
  "verification_steps": [
    {
      "step": 1,
      "action": "具体可执行操作"
    }
  ]
}
```


### Memory模型记忆
模型的长期记忆，要和上下文context、token做区别。
模型本身只接收一段文本（tokens），  Context / Memory 都是“被系统拼进去的”。
真实 Context 拼接示例（展开讲）

```text
【System / Rule】 
你是一个严谨的企业级 AI 助手...  
【Injected Memory】 
用户角色：Java 架构师 偏好：通俗解释 + 可执行步骤  
【RAG 结果】 
（从文档中检索到的 3 段内容）  
【对话历史】
 用户：xxx 助手：yyy  
【当前 Prompt】
 请评估 MetalLB 切换 ELB
```

Memory一般是存储在本地，如果是工程化的应用：一般会有上下文窗口的设置，等于记录上下文的轮次。或者本地进行文件进行记忆
```markdown
本地存储
  ├─ Memory（长期）
  ├─ 对话历史
  ├─ RAG 结果
        ↓
  Context Builder（拼装器）
        ↓
  最终 Prompt（tokens）
        ↓
       LLM
```

> ⚠️ 注意：**大模型厂商说的「100K / 200K token 窗口」= 模型一次推理时，能“同时看到”的全部上下文 token 上限**  
👉 **包含：system / rule / prompt / memory / 历史对话 / RAG 内容 / 工具返回**

不是“长期记忆”，也不是“存储能力”，而是**单次推理的“可见上下文长度”**。**举例Cursor的双下文窗口占用！！！**
```text
[System Prompt / Rule]
[Schema Prompt]
[Developer Prompt]
[历史对话 N 轮]
[Memory（摘要/长期记忆注入）]
[RAG 检索到的文档]
[工具调用结果]
--------------------------------
<= 总 token 数 ≤ 100K / 200K
```

| 维度   | 分类             | 核心                                 | 怎么用                                                                                                | 举例                                |
| ---- | -------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------- | --------------------------------- |
| 生命周期 | **短期 Memory**  | 为“当前任务”服务，用完就可以丢                   | 不写数据库，不做向量化、不长期保存<br>**会话中 → 自动总结 → 注入下一轮 prompt**                                                 | ChatGPT、Qwen等自动多轮对话记忆             |
| 生命周期 | **长期 Memory**  | 跨任务、跨时间仍然有价值的信息                    | 大模型里的典型内容、用户偏好、用户背景、稳定习惯、长期目标<br>**用户行为 → 触发规则 → 存入 Memory Store**<br>**请求时 → 挑选相关的 → 注入 context** | Cursor中的Skill、或者是ChatGPT、Qwen分组功能 |
| 作用范围 | **会话级 Memory** | 只对当前这次对话（session）有效，会话一结束，**全部清空** | 本次对话的主题、临时规则、中间结论、对齐共识                                                                             | Cursor中的session会话切换               |
| 作用范围 | **用户级 Memory** | 这个用户以后都这样？                         | 技术水平、表达偏好、使用习惯、长期身份                                                                                | Cursor中的User会话切换                  |


### RAG（Retrieval-Augmented Generation，检索增强生成）
Prompt / Schema（怎么“说清楚”）、Rule（怎么“不越界”）、Memory（怎么“记得住”）
RAG 解决二个**刚刚暴露出来的核心痛点**

> **Context 窗口再大，也不可能把“所有知识”都塞进去**
> **基础模型是有知识时效性的**


一般来说，基础模型是有知识时效性的，没有RAG或者其他的增强的裸模型，模型的知识是截止在完成训练的时间点。裸模型在**推理时**只能用两样东西，它**不能**：主动上网、自己查数据库、突破训练时间点。
> 训练时学到的统计规律 （预训练、SFT、强化学习等）
当前 Context 里给它的内容

RAG的作用，获取最新知识、私域知识，让模型先“查资料”，再“让模型回答”
`用户问题 → 检索相关资料 → 把资料塞进 Context → 再让模型生成答案`
一般RAG的落地形态：联网搜索、知识库（向量库、结构化数据库）等
### Agent智能体
前面讲了 RAG，模型已经能在回答前查资料了。  但真实工作中，很多任务并不是‘查一次资料就结束’，  而是需要多个步骤、多次判断。  这时候，就需要 **Agent**。
```text
Prompt    → 会回答
RAG       → 会查资料
Agent     → 会拆任务、做决策、串流程
```

**Agent =「大模型 + 一套固定的工具能力 + 一套行为约束配置」**
以Cursor工具为例
```text
Cursor Agent =
1️⃣ 一个基础模型（LLM）
2️⃣ 一个固定的 Agent 执行循环（Plan → Act → Observe）
3️⃣ 一组可调用的工具（Tools / MCP）
4️⃣ 一套行为与约束配置（Role / Rule / Schema）
5️⃣ 一个状态管理机制（Memory / Context）
```

| 维度         | Cursor Agent  | Coze / Dify Agent |     |
| ---------- | ------------- | ----------------- | --- |
| 面向对象       | 开发者           | 产品 / 业务 / 应用      |     |
| Agent Loop | 内置，不可改        | 内置，但可编排           |     |
| 工具         | IDE 工具（文件、代码） | API / 插件 / MCP    |     |
| Agent 创建方式 | 配置 Profile    | 可视化配置             |     |
| 是否写代码      | ❌             | ❌ / 少量            |     |
| 是否多 Agent  | ❌             | ✅                 |     |
| 是否流程化      | 隐式            | 显式（流程图）           |     |
为什么 Coze / Dify 看起来“更像 Agent 平台”？
因为它们做了 **Cursor 没做、也不适合做的事**：

| 1️⃣ 把 Agent Loop 显式化<br>节点、连线 、条件判断<br>👉 适合**非程序员理解** | 2️⃣ 把 Tool / MCP 标准化<br>`HTTP API 数据库 搜索 RAG 知识库`<br>👉 不再局限 IDE 场景 | 3️⃣ 把 Agent “变成产品”<br>一个 Agent = 一个应用<br>有 ID、有版本、有权限 |
| ------------------------------------------------------ | ------------------------------------------------------------------- | ----------------------------------------------------- |
